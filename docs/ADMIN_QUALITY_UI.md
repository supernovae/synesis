# Admin Quality UI — Design & Roadmap

Design rationale, current implementation, and future enhancement plans for the quality management UI in the Synesis admin service.

## Current Implementation (v1)

### Pages

| Page | Path | Features |
|------|------|----------|
| **Quality Dashboard** | `/admin/quality` | Summary stats (strong/adequate/weak/empty counts), filterable domain table with health badges, hit rate bars, MRR, diversity, dead-weight counts, priority curation targets |
| **Domain Detail** | `/admin/quality/domain/{key}` | Inventory breakdown (chunks, docs, authority/handler distribution), retrieval coverage metrics, dead-weight analysis, sample audit queries, unretrieved doc IDs |
| **Curator Review** | `/admin/quality/curator` | Proposed sources with quality scores (1-5), rationale, handler/authority metadata, workflow instructions |

### Data Sources

1. **Audit report file** — JSON generated by `audit_corpus.py`, shared via ConfigMap (`quality-report`) mounted at `/data/quality/`
2. **Curator proposals file** — YAML generated by `curator_agent.py`, shared via the same mount
3. **Live Milvus queries** — Real-time chunk counts per domain, used as a fallback when no audit report is available

### JSON APIs

All dashboard data is also available as JSON for programmatic access or external dashboards:

```
GET /admin/api/quality/summary       → domain health counts, live stats
GET /admin/api/quality/domains       → all scorecards (filterable by health, sortable)
GET /admin/api/quality/domain/{key}  → single domain scorecard
GET /admin/api/quality/curator       → curator proposals
```

### Technology

The current UI follows the same patterns as the rest of the admin service:

- **Server-side rendering** — Jinja2 templates via FastAPI
- **No JavaScript framework** — Pure HTML + CSS, progressive enhancement
- **Dark theme** — Matches the existing admin design language (CSS variables in `base.html`)
- **Zero build step** — No npm, no webpack, no asset pipeline

## Roadmap: Future Enhancements

### Phase 2: Interactive Actions

The admin UI should support triggering quality operations directly:

| Feature | API | Description |
|---------|-----|-------------|
| **Trigger Audit** | `POST /admin/api/quality/audit` | Create a Kubernetes Job to run `audit_corpus.py` |
| **Trigger Discovery** | `POST /admin/api/quality/discover` | Create a Job to run `curator_agent.py` for specific domains |
| **Approve Source** | `POST /admin/api/quality/curator/approve` | Move a proposed source into the active sources config |
| **Reject Source** | `POST /admin/api/quality/curator/reject` | Remove a proposed source from the proposals list |
| **Re-index Domain** | `POST /admin/api/quality/reindex/{domain}` | Trigger the indexer for a specific domain |

Implementation approach:
- Admin service creates Kubernetes Jobs via the K8s API (requires RBAC for job creation)
- Or admin calls the planner's existing `/v1/knowledge/submit` endpoint for approved sources
- Job status tracked via K8s API; UI polls for completion

### Phase 3: Trend Tracking

Store audit results over time to show improvement trends:

| Feature | Description |
|---------|-------------|
| **Historical reports** | Store each audit run in Milvus (`synesis_quality_history` collection) |
| **Trend charts** | Show domain health over time using lightweight inline SVG charts |
| **Regression alerts** | Flag domains that degraded between audit runs |
| **Delta view** | Before/after comparison for specific domains |

Schema for `synesis_quality_history`:
```yaml
fields:
  - report_id: VARCHAR (primary key, ISO timestamp)
  - domain: VARCHAR
  - health: VARCHAR
  - hit_rate: FLOAT
  - mean_mrr: FLOAT
  - total_chunks: INT64
  - source_diversity: INT32
  - timestamp: INT64
```

### Phase 4: Client-Side Enhancements

As the UI grows more interactive, introduce lightweight client-side JavaScript:

| Feature | Approach |
|---------|----------|
| **Live filtering** | Alpine.js or vanilla JS for instant table filtering without page reload |
| **Sortable columns** | Click-to-sort on dashboard tables |
| **Status polling** | Fetch job status without full page refresh |
| **Domain search** | Typeahead search across 100+ domains |
| **Chart rendering** | Chart.js or lightweight SVG for trend visualization |

Technology preference order (minimize complexity):
1. Vanilla JS (no dependencies)
2. Alpine.js (2.5kB, declarative)
3. htmx (14kB, hypermedia-driven, good for server-rendered apps)
4. Chart.js (for charts only)

### Phase 5: Source Lifecycle Management

Full lifecycle tracking for content sources:

```
Discovery → Review → Approval → Ingestion → Monitoring → Retirement
```

| Feature | Description |
|---------|-------------|
| **Source registry** | Track all content sources with status (active, pending, retired) |
| **Ingestion tracking** | Show when each source was last indexed, chunk counts, errors |
| **Quality monitoring** | Per-source retrieval quality (are chunks from this source actually useful?) |
| **Auto-retirement** | Flag sources that produce only dead-weight content |
| **Coverage map** | Visual matrix showing which sources cover which taxonomy domains |

### Phase 6: Integration with Open WebUI

Surface quality data in the end-user experience:

| Feature | Description |
|---------|-------------|
| **Confidence indicators** | Show retrieval confidence in chat responses |
| **Coverage badges** | Indicate when a topic has limited corpus coverage |
| **Feedback collection** | "Was this helpful?" buttons that feed back into quality metrics |
| **Admin widget** | Embed quality summary in Open WebUI admin panel |

## Design Principles

1. **Data before dashboards** — The CLI tools and JSON APIs are the foundation. The UI is a convenience layer, not a requirement.

2. **Progressive enhancement** — Start with server-rendered HTML that works without JavaScript. Add interactivity only when it provides clear UX value.

3. **Audit trail** — Every quality action (audit run, source approval, domain reindex) should be logged with timestamp and actor for accountability.

4. **Separation of concerns** — Quality tools produce data (JSON/YAML). The admin reads and displays it. Keep the analysis logic in the benchmark scripts, not in the admin service.

5. **Operational simplicity** — The admin service should not need ML libraries, heavy dependencies, or GPU access. It reads files and queries Milvus.

## RBAC Considerations

For Phase 2+ features that trigger K8s Jobs:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: quality-job-creator
  namespace: synesis-rag
rules:
  - apiGroups: ["batch"]
    resources: ["jobs"]
    verbs: ["create", "get", "list", "watch"]
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get", "list", "update", "patch"]
```

The admin service's ServiceAccount would need this Role bound to it.
